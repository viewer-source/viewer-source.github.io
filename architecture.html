entry points: what starts the build, what the viewer loads for editing open points: grown large, or kept twice files

The viewer shows maps from three formats (yEd GraphML, CellDesigner, SBGN-ML) in one page: a list of maps, the map, a panel with what is clicked. Each map is drawn when the site is built, by a renderer for its format, into one picture and one set of click data, so the viewer in the browser never knows which format a map came from. An editor for the layout, loaded only where the Edit tab is, draws with the same renderers in the browser and saves the map's own file back, which the build then draws again. This page shows the parts, where each lives and the open points. How to use it: Guide.

How a map travels

  1. A map file lands in maps/: pushed, added from the list with a token, or saved by the editor.
  2. The workflow Build atlas runs build.py: each map drawn by its renderer, its identifiers looked up (new ones fetched, the rest from the cache), its entry written. The build commits the results; a save that came in meanwhile starts it again from the newest version.
  3. GitHub Pages publishes the site; index.json lists the maps with their hashes.
  4. An open page checks index.json every 30 seconds and swaps in a map whose hash changed, without a reload.
  5. In edit mode the page reads the map's file, draws it again with the same renderer after each move, and saves the file a few seconds after the last one. The drawing just edited stays on screen until step 2 has caught up.

Open points

Parts of the code that have grown large or are kept twice, with the change each would take.

WhatWhy it matters, and a possible change
The viewer in one fileatlas-app.html is 227 KB, its 148 KB of script inline in every page, so a browser does not keep it between visits and every change touches one long file. Possible change: the script in its own files, as the editor's are (the sections above are its natural parts), loaded and cached as files.
core.js large2,451 lines hold selection, dragging, guides, undo, read-ahead and saving. Possible change: the read-ahead and the saving in files of their own, as they change for other reasons than the editing itself.
The editor's model by positionNodes and arcs are found by their place in the file, so adding or removing one shifts every index. Adding and removing glyphs needs a model keyed by id. yEd renumbers its ids on each save, so a lasting id is needed: a Dev id property on every node and arc, which yEd keeps.
Python twinsAbout 2,700 lines kept twice (yrender.py, cdrender.py, cd_edit.py, tidy.py), held equal by the tests, every change made in both. Needed while tools elsewhere run Python; retired once those take the JavaScript.
Built files in the historyEach save is followed by a commit of the drawings and data, so the repository's history grows with every edit. Publishing the site from a GitHub Action would keep the built files out of it.
Copies on sitesNewer atlas sites take the viewer with copy-to-site.sh; older ones carry earlier copies, not compared with the current version.
No test of the pageThe renderers and the writes are tested; switching Edit on and off and between maps is checked by hand only. Possible change: one browser test in the workflow.
