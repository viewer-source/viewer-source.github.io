entry points: what starts the build, what the viewer loads for editing large files, or code kept in two languages files

The viewer shows maps from three formats (yEd GraphML, CellDesigner, SBGN-ML) in one page: a list of maps, the map, a panel with what is clicked. Each map is drawn when the site is built, by a renderer for its format, into one picture and one set of click data, so the viewer in the browser never knows which format a map came from. An editor for the layout, loaded only where the Edit tab is, draws with the same renderers in the browser and saves the map's own file back, which the build then draws again. This page shows the parts and where each lives. How to use it: Guide.

Updated 2026-11-21, with which part may use which (before it, the live drawing of a move on GraphML and SBGN-ML maps by the yEd renderer).

Which part may use which

The parts are in layers: each uses only the layers below it, and is reached from above in one named way. A renderer never knows the page, the viewer never knows a format.

Renderers and writers (renderers/)Each other, downward only. cd_edit uses cdrender, cd_make uses cdrender and cd_edit, sbml_edit uses sbgn_edit. yrender, sbgn_edit and layout use none. A format's own rules in that format's part (graphml.js, celldesigner.js, sbgn.js, cdcreate.js). The shared parts (core.js, live.js) ask the format's part, as liveFmt() does.window.m2Editor(V), and the object it returns.
Viewer (atlas-app.html)The editor, through what m2Editor returns. Never a renderer, never a format.The include on a site's page.

Where the code goes past these lines:

  • The viewer's right-click menu calls twelve functions the editor puts on window (m2EditTurn, m2EditDelete, m2EditNodeItems, ...), beside the object m2Editor returns.
  • The viewer reads window.layout.room, the layout tool the editor loads, for the note under Padding, Complexes, when it is there.
  • The shared parts of the editor still ask which format a map is in 100 places (core.js 98, live.js 2). Each release counts them and is refused when a count grows.

How a map travels

  1. A map file lands in maps/: pushed, added from the list with a token, or saved by the editor.
  2. The workflow Build atlas runs build.py: each map drawn by its renderer, its identifiers looked up (new ones fetched, the rest from the cache), its entry written. The results are published as the site; a save that comes in meanwhile starts a newer build, which replaces the one running.
  3. GitHub Pages publishes the site; index.json lists the maps with their hashes.
  4. An open page checks index.json every 30 seconds and swaps in a map whose hash changed, without a reload.
  5. In edit mode the page reads the map's file, draws it again with the same renderer after each move, and saves the file a few seconds after the last one. The drawing just edited stays on screen until step 2 has caught up.
